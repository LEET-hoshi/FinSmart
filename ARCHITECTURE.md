# Архитектурное решение FinSmart

Статус: базовое решение для MVP. Backend выбран: Kotlin + Ktor. Серверное хранилище — PostgreSQL; Android-клиент — Kotlin + Room. Система строится как модульный монолит с одним HTTP API и одной базой данных: это соответствует объёму команды и не требует отдельного развёртывания каждого доменного модуля.

## 1. Цели и границы

Архитектура поддерживает единый пользовательский сценарий: вход или регистрация → импорт выписки → просмотр операций и аналитики → постановка цели → подбор магазинной скидки → одна рекомендация. Последние синхронизированные данные доступны офлайн.

В MVP нет банковских API, банковских логинов, платежей, нескольких торговых сетей, пуш-уведомлений, распознавания чеков, семейного доступа и банковского кешбэка. Скидка магазина и банковский кешбэк — разные типы выгоды; каталог MVP содержит именно скидки магазина.

## 2. Контекстная схема

```text
┌──────────────────────────────┐       HTTPS / JSON        ┌──────────────────────────────────┐
│ Android                       │ ◄──────────────────────► │ Kotlin + Ktor API                 │
│ UI → ViewModel → Repository   │                           │ Auth / Transactions / Analytics   │
│ Room + очередь изменений      │                           │ Goals / Offers / AI / Sync        │
└──────────────────────────────┘                           └───────────────┬──────────────────┘
                                                                          │
                              ┌───────────────────────────────────────────┼────────────┐
                              │                                           │            │
                       ┌──────▼──────┐                          ┌─────────▼─────┐  ┌─▼────────────┐
                       │ PostgreSQL  │                          │ LLM provider  │  │ Источник     │
                       │ Flyway      │                          │ только агрегат│  │ скидок       │
                       └─────────────┘                          └───────────────┘  └──────────────┘
```

Внешние интеграции не являются источниками истины для пользовательской аналитики. Сервер принимает и хранит операции, вычисляет агрегаты, а затем при необходимости передаёт ограниченный контекст провайдеру ИИ. Загрузчик скидок работает независимо от пользовательского запроса и записывает нормализованные предложения в каталог.

## 3. Компоненты

### Android

- UI и навигация: «Главная», «Операции», «Скидки», «Цели».
- ViewModel держит состояние экрана, но не содержит SQL, HTTP и бизнес-расчёты.
- Repository — единая точка доступа для UI; отдаёт Room Flow и инициирует обновление через API.
- Room хранит кэш операций, целей, скидок, метаданные синхронизации и очередь исходящих изменений.
- Токен хранится в Android Keystore/защищённом хранилище, не в Room и не в обычных настройках.
- При открытии экрана сначала показываются локальные данные, затем запускается обновление. Пустое состояние, ошибка сети и устаревший кэш различаются.

### Backend Kotlin + Ktor

Модульный монолит с доменными пакетами и общей инфраструктурой:

- `auth` — регистрация, вход, JWT, хеширование пароля.
- `transactions` — CSV-импорт, дедупликация, список и ручная смена категории.
- `analytics` — агрегаты расходов и сравнение периодов.
- `goals` — чтение и изменение целей пользователя.
- `offers` — импорт/обновление каталога и выдача действующих скидок.
- `recommendations` — подготовка безопасного агрегата, вызов провайдера и fallback.
- `sync` — обмен изменениями клиента и сервером по cursor/version.
- `common` — сериализация, ошибки API, аутентификация, логирование, конфигурация.

Каждый модуль содержит маршруты Ktor, модели запросов/ответов, прикладные сервисы и репозитории. Бизнес-правила не размещаются в обработчиках HTTP. Модули используют одну PostgreSQL и транзакции; отдельные микросервисы для MVP не вводятся.

### Загрузчик скидок

Загрузчик — отдельная задача/команда в серверном проекте, не отдельный сетевой микросервис. Он получает предложения из согласованного публичного источника или тестового файла, нормализует, проверяет обязательные поля и делает upsert по `source_id`. Ошибка источника не очищает предыдущий успешный каталог. Частота, регион, URL и допустимый способ получения данных должны быть подтверждены отдельно; ориентир «каждые 24 часа» из аналитики пока не считается гарантированным SLA.

## 4. Данные и модель владения

PostgreSQL — каноническое хранилище. Минимальные таблицы по спецификации:

- `users`: учётная запись, email и парольный хеш.
- `categories`: стабильный код и отображаемое название.
- `mcc_mappings`: соответствие MCC категории.
- `transactions`: пользователь, внешний UUID операции, дата, сумма, валюта, описание, MCC и категория.
- `goals`: пользовательская цель, целевая и текущая суммы, срок.
- `offers`: идентификатор источника, название, цены, сроки, условия, ссылка, регион и время проверки.
- `offer_categories`: связь предложения с одной или несколькими категориями.
- `sync_changes`: изменения для выдачи клиенту с монотонной серверной версией и cursor.

У пользовательских сущностей есть `user_id`; сервер извлекает владельца из проверенного JWT, а не принимает его из тела запроса. Уникальность операции: `(user_id, external_id)`. Внешние идентификаторы клиентов предпочтительно UUID. Для удаления синхронизируемых пользовательских сущностей применяется мягкое удаление/ tombstone, чтобы удаление дошло до офлайн-устройств. Физическое удаление и сроки хранения требуют отдельной политики.

Даты API передаются в UTC/ISO 8601. Для CSV дата операции соответствует согласованному формату `YYYY-MM-DD`. В MVP валюта — RUB, денежные вычисления выполняются десятичным типом с точностью до копейки; двоичная арифметика `Float`/`Double` для денег запрещена.

Системные категории: `groceries`, `cafes`, `transport`, `health`, `home`, `entertainment`, `other`. Неизвестный MCC относится к `other`. Ручная категория пользователя сохраняется и имеет приоритет при последующих обновлениях импорта.

## 5. Импорт CSV и аналитика

CSV в UTF-8 должен содержать заголовок и столбцы `operation_id,date,amount,currency,description,mcc`. Импорт идёт построчно:

1. Проверить заголовок, кодировку и значения строки.
2. Нормализовать UUID операции, дату, десятичную сумму и MCC.
3. Найти дубликат по `(user_id, operation_id)`; повторная загрузка идемпотентна.
4. Применить MCC-маппинг или `other`, не перетирая ручную категорию.
5. Сохранить корректную строку и добавить изменение в журнал синхронизации.
6. Вернуть число импортированных и повторных строк, плюс номер и причину каждой ошибочной строки.

Некорректная строка не отменяет остальные корректные строки. Сами банковские файлы не хранятся после импорта дольше, чем нужно для запроса, если команда отдельно не утвердит временное хранение.

Расходом считается `amount < 0`; сумма расходов для показа — абсолютное значение таких операций. Возвраты и входящие суммы не прибавляются к расходам в MVP. Сервер рассчитывает общий расход, суммы по категориям, топ-категорию и изменение к предыдущему равному периоду. Если предыдущий период равен нулю, `changePercent` возвращается как `null`, а не как бесконечность или произвольный процент.

## 6. Offline-first и синхронизация

Room позволяет читать ранее полученные операции, цели и скидки без сети. Сетевые вызовы обновляют кэш только после успешного ответа; локальная ошибка не должна очищать старые записи.

Для изменений клиента используется очередь с UUID операции изменения, типом сущности, целевым ID, действием, полезной нагрузкой и локальным состоянием отправки. Повторная отправка безопасна и не создаёт дубль. Клиент не назначает серверную версию по своим часам: сервер выдаёт возрастающую версию и cursor.

- `POST /sync/push`: пакет локальных изменений; сервер проверяет владельца, применяет идемпотентно и отвечает результатом каждой записи и новым cursor.
- `GET /sync/pull?cursor=...`: изменения после cursor, включая tombstone; клиент применяет их в Room транзакционно и сохраняет новый cursor.
- Конфликт версий возвращается явно. Для MVP серверная версия определяет порядок; конфликтное обновление не должно молча перетирать более новую серверную запись. Пользовательская ручная категория защищается доменным правилом.
- Удаления представлены tombstone и синхронизируются так же, как изменения.

Изменение в локальной очереди помечается завершённым только после подтверждения API. При повторной ошибке оно остаётся в очереди для последующей попытки. Автоматические повторы должны ограничиваться и не блокировать интерфейс.

## 7. API и безопасность

Основные маршруты: `/auth/register`, `/auth/login`, `/transactions/import`, `/transactions`, `/transactions/{id}/category`, `/analytics/summary`, `/goals`, `/offers`, `/ai/recommendation`, `/sync/push` и `/sync/pull`. Контракты публикуются через OpenAPI; формат ошибки единый (`code`, `message`, `details`).

- Пароли хешируются BCrypt или Argon2; исходный пароль не логируется.
- JWT проверяется на каждом защищённом запросе. Все запросы к пользовательским таблицам фильтруются по владельцу из токена.
- Токены, банковские выписки, персональные данные и секреты не попадают в логи или Git.
- Ключи провайдера ИИ и параметры источника скидок задаются через переменные окружения/секреты окружения.
- Транспорт к серверу — HTTPS в развернутой среде.
- Запросы импорта ограничиваются размером файла, числом строк и временем выполнения.
- Логи фиксируют технический результат запроса без полного CSV, описаний транзакций и токенов.

## 8. ИИ-рекомендация

ИИ не является калькулятором и не является источником финансовых фактов. Backend формирует разрешённый агрегат: период, суммы/изменения по категориям, топ-категорию и прогресс целей. В модель не отправляются CSV, текстовые описания покупок, email, IDs операций, JWT, банковские реквизиты или сырые персональные поля.

Провайдер возвращает строгий объект с `title`, `message`, `category`, `actionType`, `actionLabel`. Backend проверяет JSON, длины и допустимость кодов. Числовые значения, если они нужны в рекомендации, подставляет сервер из проверенного агрегата. При timeout, ошибке провайдера или невалидном JSON возвращается rule-based рекомендация, например о наиболее выросшей категории. При отсутствии роста или достаточных данных — нейтральный безопасный fallback без выдуманных чисел. Провайдер, регион обработки и срок хранения запросов должны быть согласованы до подключения реальной LLM.

## 9. Скидки и корректность каталога

Сущность предложения хранит `source_id`, название, категорию, обычную/акционную цену (обе могут быть неизвестны), валюту, срок, условия, URL, регион/магазин и `checked_at`. Неизвестное хранится как `null`, не заменяется догадкой.

Каталог выдаёт только действующие акции с учётом региона. Просроченные исключаются по `valid_to`. Если у источника временная ошибка, API продолжает отдавать последний успешный каталог и сообщает свежесть (`checked_at`/признак устаревания). Потенциальная экономия показывается только если есть обе цены и акционная цена корректно ниже обычной; она не записывается как фактически сэкономленные пользователем деньги.

Модуль скидок не получает историю транзакций пользователя из внешнего магазина. Персонализация выполняется внутри FinSmart по выбранной категории, агрегатам или явному выбору пользователя.

## 10. Развёртывание и структура кода

Для локальной разработки `docker compose` поднимает Ktor API и PostgreSQL. Flyway применяет версионированные миграции; начальные категории и MCC-справочник загружаются повторяемым seed-процессом. Секреты задаются через локальный `.env`, который исключён из Git; в репозитории хранится только `.env.example` без секретов.

Предлагаемое расположение:

```text
android/                    # Android-приложение Kotlin
server/                     # Ktor модульный монолит
  src/main/.../auth/
  src/main/.../transactions/
  src/main/.../analytics/
  src/main/.../goals/
  src/main/.../offers/
  src/main/.../recommendations/
  src/main/.../sync/
  src/main/resources/db/migration/
  src/test/                 # backend unit и integration tests
docs/                       # спецификации и командная документация
docker-compose.yml
README.md
```

Это целевая структура, а не описание уже созданных исходников. В текущем репозитории приложения и build-конфигурации ещё нет.

## 11. Проверяемые критерии готовности

- Повторный импорт того же CSV не создаёт дубликатов; некорректные строки не мешают валидным.
- Пользователь не может читать или менять чужие операции, цели и синхронизационные записи.
- Неизвестный MCC получает `other`; ручная категория сохраняется.
- Расходы и сравнение периодов совпадают с правилами раздела 5; нулевой предыдущий период даёт `null`.
- После успешной синхронизации приложение показывает кэш офлайн; локальные изменения отправляются после восстановления сети без дублей.
- Истёкшие предложения не выдаются; сбой источника не стирает предыдущий каталог.
- При недоступной LLM возвращается валидная fallback-рекомендация без вымышленных сумм.
- Чистое окружение стартует через Docker Compose и применяет Flyway-миграции; OpenAPI документирует согласованные маршруты.

## 12. Решения, требующие уточнения команды

- Минимальная и целевая версия Android, способ DI и выбор Retrofit/Ktor Client.
- Источник скидок, регион, правомерность и разрешённая частота загрузки.
- Политика удаления пользовательских данных и срок хранения tombstone.
- Разрешённый LLM-провайдер, регион и политика хранения запросов.
- Правило периодов аналитики (календарный месяц или пользовательский диапазон) и поведение возвратов.
- Механизм обновления JWT (refresh token или повторный вход) и срок жизни токена.
- Фактический хостинг, CI и рабочие профили окружения.
