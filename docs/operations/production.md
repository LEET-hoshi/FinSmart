# Развёртывание backend за reverse proxy

Что настроить, когда API работает не локально, а за nginx/Caddy/балансировщиком.

## Переменные окружения

Все настройки передаются только через переменные окружения. В `docker-compose.yml` они пробрасываются в контейнер `api` из `.env`; без `.env` действуют значения по умолчанию.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `JWT_SECRET` | значение для разработки | Секрет подписи JWT, не короче 32 символов. В production обязательно свой |
| `RATE_LIMIT_AUTH_PER_MINUTE` | `10` | Лимит `POST /auth/login` и `/auth/register` в минуту на один IP (общий для обоих) |
| `RATE_LIMIT_IMPORT_PER_MINUTE` | `10` | Лимит `POST /transactions/import` в минуту на пользователя |
| `LLM_ENABLED` | `false` | Включает внешний LLM-провайдер рекомендаций |
| `LLM_ENDPOINT` | пусто | Адрес провайдера, обязателен при `LLM_ENABLED=true` |
| `LLM_API_KEY` | пусто | Ключ провайдера, уходит в заголовке `Authorization: Bearer` |
| `LLM_TIMEOUT_SECONDS` | `5` | Таймаут запроса к LLM, от 1 до 30 секунд |

`LLM_API_KEY` и `JWT_SECRET` не коммитятся: `.env` в `.gitignore`, в CI и на сервере значения задаются через секреты. Сервер не пишет их в логи: `CallLogging` выводит только метод, путь и статус, а ошибки LLM перехватываются fallback-провайдером и не логируются. Контракт LLM: `docs/ai-agent.md`.

После изменения `.env` контейнер нужно пересоздать: `docker compose up -d`.

## Реальный IP клиента и rate limit

Лимит на вход и регистрацию считается по IP. Сейчас IP берётся из TCP-соединения (`call.request.origin.remoteAddress` в `common/RateLimits.kt`), заголовки `X-Forwarded-For` и `Forwarded` игнорируются. Это сделано специально: любой клиент может прислать такой заголовок с чужим IP и обойти лимит.

Следствие: если перед API стоит reverse proxy, все запросы приходят с IP прокси, и лимит в 10 попыток в минуту становится общим для всех пользователей. То же происходит на локальном стенде в Docker Desktop: клиенты за NAT видны с одного адреса.

Брать IP из заголовка можно только при выполнении всех трёх условий:

1. **API недоступен напрямую.** Порт `api` не публикуется наружу; до него может достучаться только прокси (внутренняя сеть Docker или `127.0.0.1`). Иначе клиент придёт в обход прокси с поддельным заголовком.
2. **Прокси перезаписывает заголовок, а не дописывает.** Для nginx:
   ```nginx
   proxy_set_header X-Forwarded-For $remote_addr;
   ```
   Вариант `$proxy_add_x_forwarded_for` не подходит: он сохраняет то, что прислал клиент.
3. **В Ktor включён плагин `XForwardedHeaders`** (зависимость `io.ktor:ktor-server-forwarded-header`) с доверием только последнему прокси:
   ```kotlin
   install(XForwardedHeaders) {
       useLastProxy()
   }
   ```
   После этого `origin.remoteAddress` вернёт адрес из заголовка, и `RateLimits.kt` менять не нужно. Если прокси несколько, вместо `useLastProxy()` используется `skipLastProxies(n)` по числу доверенных прокси.

Пока эти условия не выполнены, плагин не включается, а лимит, если он мешает, поднимается через `RATE_LIMIT_AUTH_PER_MINUTE`.

## HTTPS

Backend отдаёт HTTP. В production TLS завершается на прокси, а Android-клиент в release-сборке должен ходить только по HTTPS. Cleartext-HTTP допустим только для локальной разработки (эмулятор `10.0.2.2`, устройство в локальной сети).
